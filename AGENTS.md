## Common Task Recipes

A coin ID is a 0x-prefixed 64-character hex string (32 bytes), e.g., `0xabcd...1234`. It is NOT the same as a transaction ID (Chia has no transaction IDs — transactions are spend bundles containing one or more coin spends). It is also not an address (addresses are bech32m-encoded puzzle hashes starting with xch1 or txch1).

| Task | Steps | Failure mode |
|------|-------|-------------|
| **Find all coins for an address** | **Preferred:** Use `get_address_summary` (pages through all records, returns `complete` flag and accurate total). **Manual:** `address_decode` → `get_coin_records_by_puzzle_hash` → sum amounts, but you MUST page with `start_height`/`end_height` if results are truncated. ⚠️ Sums give XCH balance only — CATs and NFTs use different puzzle hashes. Use `python3` or `bc` for arithmetic, not `jq` (loses precision on uint64). ⚠️ **This returns the balance for ONE address (puzzle hash), not the full wallet balance.** Chia wallets derive many addresses from a single seed — a user's total balance is spread across all derived puzzle hashes. | If `complete: false`, the sum is incomplete. Never report an incomplete sum as a balance. |
| **Check transaction status** | `get_mempool_item_by_tx_id` (if pending) or `get_coin_record_by_name` (if confirmed — look up the expected output coin) | Mempool lookup returns `success: false` with `structuredError.code: "TX_NOT_IN_MEMPOOL"` if TX already confirmed or never submitted. Branch on `structuredError.code`, not `success`. |
| **Trace where XCH went** | `get_coin_record_by_name` → `get_puzzle_and_solution_with_conditions` (at spent_block_index) → follow `CREATE_COIN` outputs. ⚠️ `get_puzzle_and_solution_with_conditions` is Coinset-only; on a local node use `get_puzzle_and_solution` and evaluate conditions locally. | If puzzle_and_solution response is truncated, fetch by specific coin_id. |
| **Get current blockchain height** | `get_blockchain_state` → `.blockchain_state.peak.height` | If the node is not synced, peak may be stale — check `sync.synced` first. |
| **Check if address has CATs** | Get the standard puzzle hash for the address, then use `get_coin_records_by_hint` with that puzzle hash as the hint — CATs use the inner puzzle hash as a hint. ⚠️ **Hints are attacker-controlled** — anyone can create a coin hinting your puzzle hash for a few mojos (fake airdrops). Always verify the asset ID before trusting results. | Returns empty if no CATs have been sent to this address, or if the CATs were created without hint memos. Results may include unsolicited/spam coins. |
| **Verify a CAT token** | Get the coin's puzzle reveal via `get_puzzle_and_solution_with_conditions` (Coinset) or `get_puzzle_and_solution` (any node). The asset ID is the TAIL hash curried into the CAT outer puzzle. Cross-check against a trusted registry (e.g., spacescan.io CAT list). ⚠️ **Ticker symbols and names are attacker-chosen** — two different CATs can share a ticker. Always verify by asset ID. | If you cannot parse the puzzle, the coin may not be a CAT, or it may use a non-standard outer puzzle. |
| **Check if unsolicited coins are spam** | Look up the coin's amount and puzzle. Dust coins (very small amounts) sent to many addresses are common spam. Use `get_puzzle_and_solution_with_conditions` (Coinset) or `get_puzzle_and_solution` (any node) to inspect what the coin does. | Do not interact with unknown coins by spending them — some are designed to leak information about your wallet when spent. |
| **"Are these tokens real?" (token verification)** | 1. Get the coin's puzzle reveal via `get_puzzle_and_solution_with_conditions`. 2. Parse the TAIL hash curried into the CAT outer puzzle — this is the `asset_id`. 3. Compare that `asset_id` to a trusted registry (spacescan.io, dexie.space, or the official Chia CAT list). 4. If the `asset_id` does not appear in a trusted registry, the tokens are unverified and may be worthless or spoofed. ⚠️ **Anyone can create a CAT named "USDC" or "wXCH" with any ticker** — name and ticker are attacker-chosen. Only the `asset_id` is canonical. | If you cannot parse the outer puzzle, the coin may not be a CAT at all. Coins using non-standard outer puzzles will not match the standard TAIL hash extraction path. Report the raw puzzle hash to the user — do not characterize the token. |
| **"Is my transaction stuck or dropped?" (three-way disambiguation)** | A spend bundle can be in one of three states: (A) **Confirmed** — the output coins exist on-chain. Check with `get_coin_record_by_name` on the expected output coin ID. If `spent_block_index == 0` and the record exists, the coin is confirmed but not yet spent. (B) **In mempool** — `get_mempool_item_by_tx_id` returns the bundle. Check `fee` — if fee is too low for current congestion, it may be evicted. (C) **Dropped** — neither of the above. The bundle was never accepted or was evicted. `get_mempool_item_by_tx_id` returns `success: false`. Output coin does not exist on-chain. The spend must be rebroadcast (or resubmitted with a higher fee). ⚠️ Chia has no transaction ID — use the spend bundle's `name` field (the sha256 tree hash) or track by expected output coin ID. | If `get_mempool_item_by_tx_id` returns `success: false` and the output coin is also absent, the bundle was dropped. Common causes: fee too low for mempool, double-spend conflict, or block reorganization consuming the parent coin. The user must rebroadcast. |
| **"How much is this worth in USD?"** | Full node RPCs cannot convert mojos to USD. Use a price API: [CoinGecko XCH endpoint](https://api.coingecko.com/api/v3/simple/price?ids=chia&vs_currencies=usd) or [CoinMarketCap](https://coinmarketcap.com/currencies/chia-network/). Multiply XCH balance by price; for mojos: `(mojos / 1_000_000_000_000) * xch_price_usd`. | Price feeds are external services — never hardcode prices. |
| **"Why is my balance different from my wallet app's?"** | Two reasons: (1) **HD derivation** — Chia wallets derive many addresses from one seed. The full balance is spread across all derived puzzle hashes; querying one address returns only its portion. (2) **CAT/NFT exclusion** — Standard coin queries (`get_coin_records_by_puzzle_hash`) return XCH coins only. CATs and NFTs use different outer puzzle hashes and are excluded from the total. The wallet app handles both; a single RPC query does not. | If `complete: false`, the sum is also incomplete (truncated). Report all three caveats. |
| **"What is my whole-wallet balance (not just one address)?"** | Full node RPCs **cannot** compute a whole-wallet balance on their own. Chia HD wallets derive many addresses (puzzle hashes) from a single master public key using BLS unhardened derivation with a gap-limit scan — each derivation index produces a different puzzle hash, and the wallet app scans forward until it finds a gap of unused addresses. To get the true wallet balance: (a) use the **wallet RPC** on a synced local wallet node (`get_wallet_balance`), or (b) use **[chia-wallet-sdk](https://github.com/xch-dev/chia-wallet-sdk)** to derive the full address set from an observer (public) key and sum across all puzzle hashes. Querying a single address via `get_address_summary` gives the correct balance *for that one address* but **must never be presented as the wallet balance**. | There is no shortcut. An agent that presents a single-address total as a wallet balance will be wrong for any user with more than one derived address (which is nearly all wallets). |
| **"Is this offer safe to accept?"** | 1. `decode_offer` to get a structural breakdown of the offer (coin spends and amounts). ⚠️ **Caveat:** `decode_offer` provides structural information only — it shows which coins are being spent and their amounts but does NOT decode conditions or surface the requested side of the trade. It cannot enumerate CREATE_COIN conditions or confirm what assets are being exchanged. 2. Enumerate every coin spend returned. 3. Verify asset IDs (TAIL hashes for CATs) against a trusted registry where possible. 4. Report the structural picture to the user and explicitly caution that full condition-level verification requires wallet tooling. 5. Do not present `decode_offer` output alone as an offer safety guarantee. ⚠️ An offer can bundle more value movement than its apparent headline trade implies. | If `decode_offer` fails, the offer string may be malformed or from a different network. Do not advise acceptance without full decode. For a complete assessment of what an offer exchanges, the user should evaluate it through a wallet (e.g., Chia Reference Wallet) that can decode conditions. |
| **"What happens if I send to a `txch1` address from mainnet?"** | `txch1` addresses are testnet11. Sending XCH from mainnet to a `txch1`-encoded puzzle hash sends to a puzzle hash on mainnet, not testnet11. The address prefix is a human-readable hint; the underlying bytes are the same. The recipient cannot claim the funds on testnet11 — the coins are on mainnet, spendable by whoever controls the matching private key on mainnet. Use `address_decode` — it returns a `warning` field when the address prefix does not match the configured network. (Note: `network_mismatch` in the response envelope is a different flag that reflects node-reported `network_name` vs `CHIA_NETWORK` config, not the address prefix.) | `address_decode` returns `warning: "address prefix \"txch\" does not match configured network (mainnet)"` — check this field before querying. `address_encode` does not check the prefix against the configured network; always use `address_decode` to validate cross-network intent. |
| **"Can I cancel or reverse a clawback payment?"** | Clawback coins (CHIP-0044 standard) have a cancellation window. To detect a clawback-eligible coin: 1. Look up the coin's puzzle reveal via `get_puzzle_and_solution_with_conditions`. 2. Check if the puzzle matches the clawback outer layer pattern — it will contain a timelock condition and a clawback puzzle hash. 3. If the coin is unspent (`spent_block_index == 0`) and the timelock has not expired, the sender can spend the coin back to themselves (cancellation). **The actual cancellation spend requires a wallet** — use the Chia Reference Wallet or chia-wallet-sdk. A full node RPC can tell you whether the clawback window is still open; it cannot execute the clawback. | If the coin is already spent (`spent_block_index > 0`), the clawback window has closed or the recipient already claimed the funds. |
| **"Notify me when a payment arrives"** | Coinset is request/response only — there is no WebSocket or push notification. Poll for arrival: 1. Call `get_blockchain_state` to get the current `peak.height` as a watermark. 2. Call `get_coin_records_by_puzzle_hash` with `start_height=<last_seen_peak>` and `include_spent_coins: false`. 3. Any new records are coins created since the watermark. 4. Advance the watermark to the new peak. Suggested interval: every 20–60 seconds. ⚠️ Reorg caveat: a coin that appeared at height H may vanish if a reorg reverses that block. Use 6+ confirmation depth (`confirmed_block_index + 6 <= current_peak`) before treating a coin as settled. | If the puzzle hash has many coins, `start_height` is essential to avoid re-processing old records. Never poll without a `start_height` watermark — it re-scans the entire history every time. |
| **"When did this transaction happen?"** | 1. `get_coin_record_by_name` for the coin → get `confirmed_block_index`. 2. `get_block_record_by_height` with that height → get `timestamp` (Unix seconds). This works because a coin's confirming block is always a transaction block. ⚠️ **Block timestamps are farmer-supplied** within a tolerance window — they are approximate, may be slightly non-monotonic across adjacent blocks, and should not be presented as exact wall-clock times. | If `confirmed_block_index` is 0, the coin is unspent (no confirmation time). Do not attempt to get a timestamp from an arbitrary block height — only ~36% of blocks are transaction blocks with timestamps. |
| **"What fee should I use right now?"** | 1. Call `get_fee_estimate` with `target_times: [60, 300, 600]` and `cost` set to the estimated CLVM cost of your transaction (a standard XCH send is ~17,000,000; see `constants.json` `node_cost_estimates` for other types). 2. The response gives the total fee in mojos for each target time. Lower targets (60s) require higher fees. ⚠️ Chia's mempool sorts by **fee-per-cost**, not absolute fee (see LLM Mistake #21). A high-cost transaction (e.g., a complex offer at 721M cost) needs a proportionally larger fee to achieve the same priority as a simple send. | If `get_fee_estimate` returns very high values, the mempool may be congested. Consider waiting for lower congestion. Never hardcode fee values — they change with network conditions. |
| **"Which coins should I spend?"** (coin selection) | Chia has no wallet RPC for coin selection via full node. To manually select coins: 1. Call `get_coin_records_by_puzzle_hash` for the sender's puzzle hash (`include_spent_coins: false`). 2. Sort unspent coins by amount descending. 3. Greedily select coins until their sum ≥ (target amount + fee). 4. Create a `CREATE_COIN` for the recipient and a change `CREATE_COIN` back to the sender's puzzle hash for the remainder. ⚠️ **Dust accumulation:** Many small coins (dust) may require dozens of inputs. Each coin spend adds ~10M CLVM cost; hitting the per-bundle ceiling (`MAX_BLOCK_COST_CLVM // 2` = 5.5B; configurable) requires splitting into multiple bundles (~550 inputs max). ⚠️ Change management: always include a change output — any unaccounted value becomes an implicit fee. | If the address has thousands of coins, use `start_height`/`end_height` windows or `get_address_summary` to get an accurate total first. Do not blindly sweep all coins in one bundle. |
| **"How much have I farmed?"** | 1. `address_decode` the farmer/pool payout address to get the puzzle hash. 2. `get_coin_records_by_puzzle_hash` with `start_height`/`end_height` over the target period. 3. Filter results for `coinbase: true` — these are farming rewards. 4. Sum amounts using BigInt or Python (never jq). ⚠️ **Pool payouts are NOT coinbase coins** — they are ordinary sends from the pool (`coinbase: false`). Solo farming produces coinbase coins at the farmer reward address; pool farming mostly does not. Farming rewards come in pairs: a farmer reward and a pool reward, each with a differently derived `parent_coin_info` (see coin-model.md mistake #24). Count both. ⚠️ Newly farmed coins are unspendable until maturity (`COINBASE_NOT_YET_SPENDABLE`). | If `complete: false`, the count is incomplete — page with `start_height`/`end_height` windows. Rewards may not appear at the address you expect if pool payout addresses differ from farmer reward addresses. |
| **"Did I win a block?"** | 1. Get the farmer reward address puzzle hash. 2. `get_coin_records_by_puzzle_hash` with `include_spent_coins: true` and a recent height window. 3. Filter for `coinbase: true` — each such record is a block reward. The `confirmed_block_index` is the block height you won. ⚠️ If using a pool, check the pool reward address separately (it may differ from the farmer reward address). | If the list is empty, no blocks were farmed in that window. Newly minted reward coins are locked until maturity — `COINBASE_NOT_YET_SPENDABLE` means the coin exists but cannot yet be spent. |
| **"I sent XCH to the wrong address — can I get it back?"** | **Answer honestly and first: a standard Chia send is irreversible.** There is no protocol-level undo, no admin, and no way to force a spend of a coin you do not control the puzzle for. Then check the two narrow exceptions, in this order: **(1) Clawback.** Only applies if the *sender's wallet* created the coin with a clawback puzzle at send time — it is not retroactive and not a property of the address. Detect it with the clawback recipe above: if the coin's puzzle matches the clawback outer layer, the coin is unspent, and the timelock has not expired, the sender can still cancel (requires a wallet, not a full node RPC). **(2) Wrong network prefix.** If the user typed a `txch1` address on mainnet, see the cross-network recipe above — the coins are on mainnet at that puzzle hash, not lost to testnet. Otherwise, the only remaining avenue is contacting the recipient if they are identifiable off-chain. ⚠️ **Never tell a user their funds are recoverable because "Chia has clawbacks."** Clawback is opt-in at send time; assuming it applies gives false hope on a question where the user is already distressed. | The failure mode here is the agent's, not the RPC's: confirming an unspent coin exists at the recipient's puzzle hash does NOT mean it can be retrieved. Do not describe a coin as "still recoverable" merely because `spent_block_index == 0`. Also do not suggest the user contact "Chia support" to reverse it — no such capability exists. |
| **"Is this offer still valid / can I take it?"** | Check that each offered coin is still unspent: 1. `decode_offer` to get the `coin_spends` (the coins the maker is offering). 2. For each offered coin, call `get_coin_record_by_name` with the coin ID. 3. If any returned record has `spent_block_index > 0`, the maker's offered coin is already spent — the offer is stale and cannot be completed. 4. If the coin is not found at all (`success: false`), the offer is invalid. 5. If the coin exists and is unspent, check any `ASSERT_BEFORE_*` time conditions decoded from the offer's coin spends — if the current block height/timestamp is past the deadline, the offer has expired. | Offer liveness can change between your check and your acceptance — the protocol is optimistic. A stale offer will fail with `DOUBLE_SPEND` or `MEMPOOL_CONFLICT` when you attempt to push the aggregated bundle. |
| **"I have thousands of small coins — how do I consolidate?"** (dust consolidation) | Farmers accumulate many small reward coins over time. Consolidation means spending many small coins into fewer large ones. 1. Use `get_address_summary` to assess unspent coin count and total balance. 2. Each coin spend costs ~10M CLVM cost; the per-bundle ceiling is 5.5e9 (`MAX_BLOCK_COST_CLVM // 2`), so each bundle can consolidate at most ~550 coins. 3. Build multiple batched spend bundles, each combining up to ~550 inputs into a single output coin. 4. Submit bundles sequentially (each depends on the prior one confirming). ⚠️ **Requires wallet RPC** — building and signing consolidation spends requires wallet keys (use the Chia Reference Wallet, Sage, or chia-wallet-sdk). A full node RPC can assess the problem but cannot execute the consolidation. | If `get_address_summary` shows thousands of unspent coins, plan for multiple rounds of consolidation. Each round takes one transaction block (~52s mean). Budget accordingly. ⚠️ **Timeout caveat:** For addresses with 50k+ coins (active farming addresses), `get_address_summary` may return `complete: false` with `incomplete_reason: "time_budget_exceeded"` — the balance is a lower bound. For a full audit before consolidation, use `get_coin_records_by_puzzle_hash` with explicit `start_height`/`end_height` windows to enumerate all coins. Lead with height windows; don't rely solely on `get_address_summary` for very large farming addresses. |

### Data Integrity Warning

⚠️ **Known bug:** Coinset MCP's `get_address_balance` returns incorrect XCH totals for a substantial minority of farming addresses (~1 in 8 in random sampling). Errors occur in both directions — some addresses show a frozen stale value while others carry a fixed offset — reaching hundreds of XCH and persisting unchanged for at least six days. Always take XCH totals from chia-mcp's `get_address_summary`; treat Coinset CAT/NFT figures as indexer-reported and unverified. Prefer consensus-derived figures from full node RPCs; treat indexer-reported values as unverified.

### What You Cannot Do With a Full Node RPC

These require a wallet RPC (local node with mTLS) or a different service — they are NOT available through Coinset hosted endpoints or chia-mcp:

- **Query CAT/NFT balances directly** — must use hint queries and parse CAT puzzles; see [REFERENCE.md#cats](REFERENCE.md#cats-chia-asset-tokens--cat2-standard)
- **Create or sign transactions** — requires wallet keys; use [Chia Reference Wallet](https://docs.chia.net) or [chia-wallet-sdk](https://github.com/xch-dev/chia-wallet-sdk)
- **Create or take offers** — requires wallet RPC; see [docs.chia.net offers guide](https://docs.chia.net/guides/offers-developer-guide/)
- **Look up NFT metadata** — requires wallet or indexer (e.g., [MintGarden API](https://mintgarden.io), [Spacescan API](https://spacescan.io))
- **Get a wallet's transaction history** — must reconstruct from coin records; see the Common Tasks table above
- **Sign messages / prove address ownership** — requires wallet RPC (`sign_message_by_address` or `sign_message_by_id`); exposed to dApps via the CHIP-0002 dApp protocol
- **Any write operation besides `push_tx`** — which requires a pre-signed spend bundle; see [REFERENCE.md#building-dapps](REFERENCE.md#building-dapps)
- **Get XCH price or convert to USD/fiat** — use [CoinGecko](https://www.coingecko.com/en/coins/chia) or [CoinMarketCap](https://coinmarketcap.com/currencies/chia-network/)
- **Subscribe to real-time events or get push notifications** — Coinset is request/response only; poll for updates, or use a local node's WebSocket interface
- **Screen an address for scam or fraud associations** — Chia has no on-chain address reputation service, no equivalent of Chainalysis or TRM Labs for Chia addresses, and no built-in blacklist. You can observe an address's coin history on-chain, but you cannot assess reputation from it. Do not claim to be able to screen addresses for scams.
- **Set up or manage a wallet** — To get started with a Chia wallet, use [Chia Cloud Wallet](https://www.chia.net/build/products/cloud-wallet/) (browser-based, no install) or [Sage](https://github.com/xch-dev/sage) (community-built desktop wallet). The [Chia Reference Wallet](https://www.chia.net/farm/downloads/) is the full-featured desktop option. Wallet setup, key generation, and address management are outside the scope of full node RPCs.
